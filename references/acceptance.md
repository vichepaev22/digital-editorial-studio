# Acceptance checklist

Release blockers: unsupported central claims, fabricated measurements, broken primary navigation, inaccessible core action, leaked secrets or personal data, failed build, or unverified deployment presented as live.

For each gate record status (pass/fail/not run/not applicable), evidence, environment, date and next action.
1. Evidence: material claims have a source locator; units and caveats match; interpretations labeled.
2. Editorial: intended audience can identify thesis, choose a route, locate sources; illustrations labeled.
3. Design: coherent typography and art direction; readable mobile and desktop; rights recorded.
4. Accessibility: keyboard, focus, zoom/reflow, contrast, labels, reduced motion, automated scan and manual checks.
5. Functionality: all primary reader tasks tested, storage failure handled, external links checked, exports valid.
6. Performance: lab results documented; field metrics separately labeled or unavailable.
7. Privacy/security: no unexpected collection, secrets or user text transfer; consent verified where needed.
8. Release: branch/commit, test result, deployed URL and rollback procedure.
9. User validation: comprehension tasks and observed failures; no extrapolation from small samples.

Use a prioritized issue register: severity, evidence, proposed change, acceptance test, expected impact, effort, owner. Distinguish observed defect from hypothesis.
